For marketers

The list is the product

Every screen points at one outcome: the right people receive a message they can read, and the list survives the send.

Blocks, not HTML

Eighteen block types, a live canvas, revisions, and saved blocks. Preview and send run the same renderer, so the inbox matches the editor.

Audiences from tags and fields

tag:news -tag:internal plus meta:plan=pro, compiled to parameterised SQL. Pending, unsubscribed and suppressed rows never enter an audience.

A campaign is a frozen snapshot

Content and metadata freeze at schedule. Editing the template afterwards cannot change an in-flight send, and replaying a queue batch sends nothing twice.

Every send has a web version

/p/<campaign id> renders the frozen snapshot. A signed per-recipient token keeps merge tags and unsubscribe working for the reader.

Automations stay linear

Four triggers, six step types, versioned runs. No workflow canvas, no branching graph, no hidden state.

Honest analytics

Clicks are the real metric. Opens are approximate because Apple Mail and corporate proxies pre-fetch pixels, and the app says so.

For builders

One Worker, no hidden service

The SPA, API, media proxy, MCP endpoint, OAuth provider, queues and cron job deploy together. There is no second service to keep alive.

Cloudflare-native

Hono on Workers, D1 for data, R2 for media, Queues for dispatch and email events, Cron for the sweep. One wrangler deploy.

Five integration surfaces

A public subscribe endpoint for marketing sites, signed outbound webhooks, scoped API keys, transactional email, and an OAuth-protected MCP server.

The email layer is its own package

@postwren/email is an IR plus a renderer that emits only table/tr/td with inline styles. No React, no DOM, no Node APIs.

Deliberately narrow

No workflow canvas, no A/B testing, no multi-tenant billing. The parts that are missing were left out on purpose, not postponed quietly.

Interfaces

Four ways in, one access model

Every surface uses the same envelopes, scopes and suppression rules. The examples below are the shapes you will actually handle.

Newsletter form

Publishable key, per-key origins, honeypot and optional double opt-in.

curl -X POST https://mail.example.com/api/public/subscribe \
  -H 'authorization: Bearer pk_live_...' \
  -H 'content-type: application/json' \
  -d '{"email":"ada@example.com","tags":["news"]}'

Transactional email

A scoped pwr_ key, one recipient, no campaign or recipient rows. 

curl -X POST https://mail.example.com/api/v1/emails \
  -H "authorization: Bearer $POSTWREN_KEY" \
  -H 'content-type: application/json' \
  -d '{"to":"ada@example.com","subject":"Your receipt","html":"<p>Thanks.</p>"}'

Signed webhooks

Retried with backoff, logged per attempt, verified with hex HMAC-SHA256.

{
  "id": "whd_...",
  "event": "subscriber.created",
  "created_at": 1767225600,
  "data": { "id": "sub_...", "email": "ada@example.com" }
}

Agents over MCP

25 scoped tools at /mcp, for API keys or an OAuth connector.

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "list_subscribers",
    "arguments": { "tag": "news", "limit": 25 }
  }
}

What Postwren does not do

  • No workflow canvas or branching automation graph. Runs are linear by design.
  • No A/B testing, no send-time optimisation, no paid-tier feature gating.
  • No multi-tenant billing or account hierarchy. One install usually means one list.
  • No deliverability guarantee. Cloudflare owns the MTA; you own the domain and the list.
